# 设计文档架构审查修订

## Goal

将现有产品、领域、架构、数据、部署和路线图文档收敛为一套相互一致、能够指导实施与验收的资源架构。修订应消除跨文档冲突，明确权威事实源、状态机、时间语义、幂等约束、权限撤销和异步任务可靠性，同时保留家庭学习与训练产品已经确认的核心意图。

## Background

- 文档集以 `CONTEXT.md` 为术语来源，以 `docs/product-scope.md`、`docs/user-flows.md`、`docs/data-model.md`、`docs/architecture.md`、`docs/deployment.md`、`docs/implementation-roadmap.md` 和 ADR 为主要设计来源。
- 架构审查发现：补填截止时间冲突、积分唯一约束无法由现有字段实现、家庭成员与亲子关系双重事实源、即时撤权与异步授权投影不兼容、训练每日有效会话唯一键可能被版本切换绕过。
- 其他高风险问题包括：多实例计划表达不足、时间语义混杂、缺少 transactional outbox、关键领域 Module 遗漏、删除与紧急访问契约不足、路线图决策状态过期、投影缺少版本维度、审计 metadata 过于自由以及运维资源目标缺失。
- 本任务仅修订设计与规划文档，不实现产品代码、数据库迁移或云基础设施。

## Requirements

- R1：为跨文档规则建立唯一权威表达；移除旧规则，不允许使用“以下文覆盖上文”的方式处理冲突。
- R2：统一迟完成、人工补填、奖励截止和事实更正的时间词汇与边界，补填奖励截止采用现有已确认规则：计划日次日家庭时区 `18:00`。
- R3：重构家庭资源模型：亲子关系作为授权事实源；家庭成员归属作为明确派生投影或具备可验证不变量的持久资源；定义多学生家庭、部分解除、最后一位家长离开和并发关联的行为。
- R4：定义敏感资源即时撤权策略；授权投影不得单独作为放行依据，并明确缓存、会话、媒体链接与撤权生效要求。
- R5：将计划实例标识、时间点、多实例生成、计划版本、未来重建和幂等键统一建模。
- R6：将日程状态事件与版本化事实分离；系统事实、人工事实、确认、更正和作废具有唯一权威来源。
- R7：重构积分资源链路为“事实版本 → 结算 → 不可变流水 → 余额投影”，使数据库可以实施结算幂等、冲销关系和投影重建约束。
- R8：训练每日有效资格基于稳定训练标识定义，投影必须携带训练定义版本与年龄档。
- R9：补充 PostgreSQL transactional outbox、Worker 租约/重试、死信、定时任务去重、事件版本和投影重建策略。
- R10：补齐家庭访问、每日总结隐私、数据生命周期、兑换、审计/紧急访问等深 Module 的 Interface 与 Seam；避免调用方直接操作底层表或余额。
- R11：为删除、导出、备份恢复、紧急访问和审计元数据建立可执行的资源处置与安全约束。
- R12：统一路线图中的决策状态、里程碑依赖、验收时间点与回滚描述；删除与已确认 ADR 冲突的“待确认”项。
- R13：补充容量分档、SLO、故障域、RPO/RTO、队列积压、恢复演练和对象存储引入时机等运行资源设计。
- R14：升级 ADR 格式，包含状态、日期、上下文、决策、后果、风险、复审触发条件和替代关系。
- R15：保持已确认的核心产品约束：仅家庭场景、5–18 岁、固定 `Asia/Shanghai`、学生确认关联、配置创建者所有权、不可变积分流水、私密总结逐家长授权、MVP 不引入 AI/语音。

## Out of Scope

- 编写业务代码、数据库迁移、测试代码或部署配置。
- 选择具体云厂商、身份库、ORM 或消息中间件。
- 为延后功能补齐完整产品设计，包括 AI、语音、错题库和家长推送媒体试点。
- 代替上线前的中国大陆法律与未成年人数据合规评审。

## Acceptance Criteria

- [ ] 文档中不再同时存在 `06:00` 与 `18:00` 两种补填奖励截止规则。
- [ ] 家庭、成员、亲子关系、授权范围和解除关系分别有明确事实源及事务不变量。
- [ ] 每个关键状态迁移均说明操作者、前置条件、幂等行为、审计结果和失败结果。
- [ ] 计划多实例、事实版本、积分结算、流水冲销和训练每日有效资格都能映射为数据库唯一约束。
- [ ] 敏感读取不依赖最终一致的授权投影放行，解除关系后的撤权机制可测试。
- [ ] 所有关键异步流程说明事务入队、重复执行、重试、死信、监控与恢复方式。
- [ ] 数据模型中的字段、唯一键和正文约束互相一致，不再引用实体中不存在的字段。
- [ ] 产品范围、用户流程、数据模型、架构、部署、路线图和 ADR 对同一规则使用一致术语与数值。
- [ ] 路线图中的每个里程碑可独立演示、验证和回滚，验收场景不引用尚未交付的后续能力。
- [ ] 文档明确哪些能力是 MVP、延后或上线前阻断项，并保留原始需求到最终范围的可追溯关系。

## Key Decision

采纳更小的纵向 MVP 闭环，并重排路线图；不删除最终产品能力。首个可用闭环固定为“单家长—单学生—单训练—单正式计划—固定积分模板”，然后再引入多家长关系、训练扩展、私密总结、兑换、删除/导出和运维强化。
