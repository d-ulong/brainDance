## 3. 图片上传故障（R-MEDIA-01）

### 3.1 已获得的证据

- 用户报错：`BRAIN_DANCE_MEDIA_ROOT must be an absolute configured path`。
- 实际调用 `resolveConfiguredMediaRoot` 并加载 `.env.local`，复现相同错误；该环境加载后媒体根目录未配置。
- `private-media-store.ts:37` 起的校验中，空值产生上述错误，相对路径产生另一条 `must be an absolute path`。候选绝对路径 `D:/work/codex/brainDance/.braindance-media` 通过路径校验，未创建目录或写文件。
- `scripts/start-closed-pilot.ps1` 会显式设置本机私有媒体目录并在启动前检查其可写性；本机运行时配置使用 `local-no-scan`，不将其表述为病毒扫描。
- `media-scanner.ts` 当前只有测试扫描器与拒绝上传的兜底扫描器；在所加载环境中返回 `scanner_not_configured`。仅配置目录不足以宣告完整修复；本轮未验证运行中 Web 进程的扫描器环境。

结论：已确认本机配置可复现缺少媒体目录的直接故障；按旧策略还会遇到扫描器未配置。用户本轮明确暂不需要图片扫描，因此本次本机方案不新增扫描组件，也不能伪称已做恶意文件扫描。

### 3.2 修复需求与验收

- 启动入口明确配置私有媒体目录并检查路径、可写性；文档说明启动、备份与故障排查。不可把图片放进 `public` 或暴露磁盘路径。
- 为普通用户显示可操作的中文提示，如“图片服务尚未配置，请联系维护者”，详细配置错误仅在维护诊断中体现；不得出现假上传成功。
- 已确认本机试用暂不做恶意文件扫描；仍保留扩展名/MIME/真实类型和大小校验、图片解码重编码、尺寸/资源限制、授权和私有存储。重编码不等于杀毒，不能承诺排除全部恶意文件风险。
- 本机不扫描策略必须显式限定在本机试用配置中并如实标识，不能将 `test-clean` 冒充真实扫描或无条件放开其他环境；正式对外使用前重新评估扫描要求。
- 使用正常 JPG/PNG/WebP 在真实启动入口完成上传、发布、授权读取；验证错误格式、超限、损坏图片和无权限读取。当前上限沿用每文件 10MB。

## 4. 独立计划与学生分配（R-PLAN-01/02）

### 4.1 已明确的用户操作

- 顶部提供独立“计划”入口，不要求先进入某个学生详情才可创建和管理计划。
- 支持新建、编辑、查看、复制计划；创建内容与指定学生是分开的操作。
- 一套计划可以指定给不同学生，一个学生可以绑定多套计划，能在已绑定计划中切换。
- 已确认：同一个学生同一时段只启用一套正式计划；切换到另一套时替换当前启用计划，旧绑定保留以便以后切回，不同时叠加多套计划的日程。
- 计划显示内容项摘要、适用日期及分配情况；学生页面可进入“已绑定计划”，不是唯一管理入口。

### 4.2 建议方案（待确认）

- 内容定义与学生绑定分离：计划保存配置，绑定保存学生、采用版本、生效区间及启停状态；学生执行记录独立。
- 复制生成独立草稿，复制内容、时间配置、积分配置，但不复制学生绑定、日程、完成记录或积分流水；后续编辑互不影响。
- 编辑已分配计划产生新版本，展示受影响学生并明确何时应用；不得因编辑或复制改写历史执行与积分。
- 单套启用约束必须按学生及绑定生效区间检查；两个家长并发切换时不能形成双启用。具体并发冲突及重试契约在实施设计中冻结。
- 仅在当前有效关系及配置所有权范围内分配、编辑和切换；独立入口不扩大跨家庭权限，学生不因此获得修改正式积分配置的权限。

## 5. 日程更新与手动生成（R-SCHEDULE-01）

已明确：绑定及切换后更新半个月日程，并可手动选择起止日期生成。

已确认的自动窗口与切换规则，以及尚待确认的手动范围建议：

- “半个月”采用连续 15 个家庭自然日，而非自然月上/下半月；窗口含生效日 D 至 D+14，时区固定 `Asia/Shanghai`。
- 自动生成取窗口、绑定有效期、计划有效期、内容项有效期的交集；到期后不继续生成。
- 已确认切换默认次日生效，也可选择今天。保留历史、已开始、已完成及已结算记录；仅取消生效范围内旧计划尚未开始的日程，再生成新日程。选择今天时不取消今天已开始的任务，也不重建已过去时段的任务。取消不是“未完成”，不得因切换自动罚分。
- 已手动生成、超出 15 日窗口的旧计划未来日程，也要在旧绑定失效时停止生效，不能切换后残留。
- 手动生成先选择学生、已生效绑定和日期范围，预览新增/保留/冲突数量再确认；首版建议仅生成今天及未来，单次最多 90 天，超限明确提示。这些范围限制不是用户已批准要求。
- 同一学生、绑定、内容项、计划日期及执行时段不重复生成；重试、范围重叠、多人同时操作应幂等。时间重叠应提示，不能因名称相同合并不同内容。
- 写入失败不能呈现“已切换但日程未更新”；同步事务或异步可恢复流程的技术选择在实施设计中明确，用户必须能看到处理中、成功或失败。

## 6. 多内容计划与条件积分（R-ITEM-01/R-POINT-01）

### 6.1 内容项字段

| 字段 | 要求/建议 |
| --- | --- |
| 名称、说明、排序 | 一套计划多项内容，各项独立显示和完成 |
| 起始日期、结束日期 | 支持计划有效期；建议内容项继承计划日期并可在其范围内缩小 |
| 执行日期/重复方式 | 已确认四种互斥方式：指定某天、每天、每周指定星期、每月指定日期；按内容项配置 |
| 执行预期时间 | 用户要求包含；建议定义为当天预期开始时刻，主要用于日程展示 |
| 最晚执行时间 | 可不设置；已确认指最晚开始时间，以实际开始时刻判断是否迟执行 |
| 完成时长 | 可不设置；已确认指开始至完成的耗时上限（分钟），不是最低坚持时长 |
| 实际开始/完成/耗时 | 保存执行事实及来源；人工补录计分沿用家长确认，不能只相信客户端自报计时 |
| 积分条件及各档分值 | 每个内容项分别配置；不提供任意脚本或自由条件树 |

预期时间、最晚时间、时长是不同维度。时间和时长边界建议使用“等于阈值视为达标”；跨午夜及暂停计时尚未要求，首版不隐式支持。

重复方式要求：

- 指定某天：只在所选具体日期产生一次日程，不因窗口滚动重复生成。
- 每天：有效日期区间内每天一次。
- 每周星期几：按所选星期生成，不是简单间隔七天；建议可多选周一至周日，待确认。
- 每月几号：按自然月日期生成，不是间隔三十天；建议可多选 1–31 日，当月不存在的日期跳过，不挪到月末，待确认。
- 所有方式都要与计划/内容项/绑定有效区间及生成窗口取交集；重复生成相同发生日期不增加第二条任务。

已确认示例：最晚开始 19:00、耗时上限 30 分钟；18:50 开始、19:15 完成，属于未迟执行且时长达标，而不是因完成晚于 19:00 判为迟执行。

### 6.2 条件矩阵

以下条件矩阵已由用户确认，不预设具体分数。每项每次执行只命中一个结果；未配置必需分值时禁止启用，而不是默认为任意奖扣。

| 配置模式 | 实际结果 | 独立分值 |
| --- | --- | --- |
| 有最晚时间、有时长 | 未超过最晚时间，时长内完成 | A：正常完成分 |
| 同上 | 未超过最晚时间，超出时长但完成 | B：超时完成分 |
| 同上 | 超过最晚时间，时长内完成 | C：迟执行但时长达标分 |
| 同上 | 超过最晚时间，超出时长但完成 | D：迟执行且超时分 |
| 同上 | 截止结算时仍未完成 | E：未完成分 |
| 无最晚时间、有时长 | 时长内完成 | F：达标分 |
| 同上 | 超出时长但完成 | G：超时完成分 |
| 同上 | 未完成 | H：未完成分 |
| 无时长（成功/失败模式） | 完成 | I：成功分 |
| 同上 | 未完成 | J：失败分 |

- 已确认“迟执行且超时完成”与“根本未完成”分开；等于时间或时长阈值视为达标。
- 无最晚时间时不判断早晚；无时长只分成功/失败，若仍填写最晚时间仅作日程提示、不参与积分。
- 已确认每档可提前配置整数正分、0 分和负分；本轮不增加积分总额上限或上限管理功能。负分只能按预先生效的规则结算，不允许事后临时处罚；仍做整数合法性及存储溢出校验。
- 已确认计划日期次日 18:00 为最终结算点，沿用既有规格中的补填限制。“未完成”不是一超过最晚时间就成立，否则与迟执行完成积分冲突；现有完成 +10 代码不能替代新增未完成自动结算实现。
- 缺少必要计时事实不应自动视为达标，也不能将“缺少事实”强行等同于“未完成”；沿用事实确认与明确模板规则。
- 分值规则版本与生成日程绑定；修改规则不直接重写已发生的积分。事实更正经重算/反向流水纠正，防重复奖励、正负同时结算和跨学生混算。

### 6.3 奖扣上限现状更正

截至 2026-09-10 的代码核对：

- 当前家长计划页仅提供“启用固定积分规则（+10）”，没有奖扣上限设置页面；管理员也没有对应入口。
- `src/db/schema/points.ts:82` 的模板表虽有 `limits` 和 `negativeEffectSchema` 字段，但 0011、0015 迁移内两个内置模板将这两项设为 NULL。
- `point-rule.service.ts` 启用时只接受模板及错误数阈值，把模板 effect 拷贝到规则版本；当前结算模块未使用模板 `limits` 实施上限。
- 因此“保留既有奖扣上限”是不准确的现状描述：它是既有规格要求，并非现有可设置、已执行能力。无需让用户去寻找不存在的页面，也不应指导用户直接改数据库作为产品配置。
- 已确认本轮不增加积分总额上限及其设置入口，按各内容项预设分值结算。旧规格要求的管理员模板奖扣上限不适用于本轮新增的内容项条件积分，作为后续能力另行规划。

## 7. 独立家长推送（R-PUSH-01）

### 7.1 已明确

- “学生”下的“推送”二级页签进入后直接管理推送，不要求从某个学生进入。
- 支持按学生、日期、tag 筛选，筛选结果在同一页面呈现，可清空筛选。
- 推送内容创建与单个学生解耦，不再要求为每名学生重复编辑相同内容。

### 7.2 已确认的接收范围与筛选口径

- 内容独立保存，发布时选择一名、多名或全部当前有权接收的学生；可保存未指定接收人的草稿。“不绑定单个学生”不等于无需接收范围或默认向全家庭开放。
- 日期筛选默认按发布时间（家庭时区、首尾日期都包含），预约内容按预约发布时间，未发布草稿按创建日期并明确标识；不能把几种日期混用而不说明。
- tag 支持多标签、去首尾空格、去重；筛选建议学生/日期/tag 之间取交集，多 tag 默认命中任意一个。具体口径可随确认调整。
- 每个接收学生的作答与完成记录独立；其他学生不能因为共用内容而看到彼此作答。家长仍须逐学生复核授权。
- 图片不能只删除现有 `studentId` 校验就跨学生复用；草稿媒体归属、发布授权、下载能力、引用和删除清理均需随接收范围重设计。共享一个物理文件不代表共享读取权限。
- 沿用文本/链接/图片、立即/预约发布、创建者编辑、审计及撤销逻辑；解除关联后不能保留不应有的访问权。预约发布时再次校验接收范围。
